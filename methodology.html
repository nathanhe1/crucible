Methodology

How we measure behavior that unfolds over time

A single-turn benchmark asks whether an answer is right. A stateful environment asks something harder: whether a sequence of choices, each made on partial information, adds up to what you wanted. This is how we keep those measurements honest.

    Contents

      Specify the task before you score it

      Most disagreements about an evaluation turn out to be disagreements about the task. Before any model touches an environment, we write down four things and put them under version control alongside the code.

      • The goal. Stated in terms of the world, not the transcript. "Keep the warehouse stocked without exceeding the purchasing budget" is a goal; "produce a reasonable restocking plan" is not.
      • The observation. Exactly what the agent sees at each step, including what it is deliberately not shown. Hidden state is part of the design, and leaking it by accident is one of the most common ways a benchmark becomes easy.
      • The action space. The legal moves, their arguments, and what happens on an illegal or malformed one. We prefer explicit penalties or no-ops to silent retries, because retries hide how often a model fails to follow the interface.
      • The budget. Steps, tokens, tool calls, and wall-clock time. A policy that succeeds only with an unlimited budget is a different policy from one that succeeds within the budget a deployment will actually allow.

      Scoring that matches intent

      A score is a claim about what you care about. When the claim is wrong, optimizing it makes things worse. We keep three kinds of measurement apart and report each one on its own line.

      Completion asks whether the goal was reached. Constraint violations count the times the agent did something it was told not to do, whether or not it finished. Prediction error measures how far the agent's expectation of an action's effect was from what actually happened. An agent can complete a task while breaking three rules; another can follow every rule and never finish. Folding these into one number hides exactly the trade-off a decision-maker needs to see.

      The separation matters most for world-model evaluation. If a model is asked to predict the next state before it acts, the accuracy of that prediction is a property of its understanding, and task success is a property of its policy. A model can stumble into success with a poor model of the world, or understand the world well and still choose badly. We score predictions against the realized transition at each step and keep that score out of the task reward entirely, so neither can quietly subsidize the other.

      Controlled comparisons

      The point of comparing two models is to learn something about the models. That only works if everything else is held fixed: environment version, seeds, opponent policies, tool implementations, prompt scaffolding, budgets, and decoding settings. We run both arms on the same set of seeds, so each episode has a matched counterpart and the comparison is paired.

      Sometimes a perfectly matched comparison is impossible. One model needs a different tool format, or a provider does not expose a setting. When that happens we don't pretend otherwise. Every report lists the differences between arms in a table at the top, before any results, so a reader can judge how much of the gap might belong to the setup rather than the model.

      Repeated trials and how many you need

      Stateful environments are noisy. The same model on the same task can score very differently depending on the seed, on sampling, and on how the rest of the world happens to move. One run tells you almost nothing; ten runs tell you roughly where the mean is. We report means with 95% confidence intervals, and we decide how many trials to run before we look at results, not after.

      The right number depends on two things: how variable the score is, and how small a difference you need to be able to detect.       Two practical notes. First, the standard deviation should come from a pilot run in the same environment, not a guess; we usually spend a small fraction of the budget on a pilot for exactly this reason. Second, if you plan to compare many models or many tasks at once, the per-comparison threshold needs to tighten, and the trial count rises with it.

      Validating the benchmark itself

      A benchmark can be wrong in ways that make every model look better than it is. Before we trust an environment, we try to break it.

      • Grader-exploit probes. We write adversarial policies whose only purpose is to score well without doing the task: emitting the success string, exploiting a lenient parser, triggering an early termination that counts as a win. If any of them score above chance, the grader gets fixed before a single real model is run.
      • Trivial-policy baselines. A random agent, an agent that always takes the same action, and a simple scripted heuristic. If a frontier model barely beats "always wait," the environment is not measuring what we hoped, or the task is easier than it looks.
      • Contamination and held-out procedures. Seeds, scenarios, and configuration files for the reporting set are generated after the environment is frozen and never published. Public examples come from a separate pool. When a scenario leaks, it is retired, and we keep a record of which results it touched.

      Failure attribution

      When an episode goes wrong, the useful question is not just "did it fail" but "what failed." Was it the model, which saw the right information and chose poorly? The tool, which returned a malformed result or timed out? Or the environment, which had a bug, an ambiguous rule, or a transition that didn't match its own specification?

      Each failed trajectory is tagged with one of these causes, and the tag is checked by replaying the episode. Tool and environment failures are logged and excluded from model scores, but they are reported, because a model that copes gracefully with a flaky tool is showing a skill worth knowing about. Every attribution is linked to the step where the failure first became visible, so a reader can check our call rather than take it on faith.

      What a commissioned engagement delivers

      When a team commissions an evaluation, they get more than a ranking. A standard engagement includes:

      • A written environment specification, versioned, covering state, transitions, observations, actions, budgets, participants, and scoring.
      • The environment itself, packaged so your team can rerun any episode from its seed.
      • Full trajectories for every run, in a documented schema, with fork metadata where we branched.
      • A results report with separate completion, violation, and prediction scores, confidence intervals, and a table of every difference between compared arms.
      • A validation appendix: exploit probes attempted, baseline scores, and the held-out procedure used.
      • A failure analysis that attributes errors to model, tool, or environment, with links to the exact steps.

      We also hand over our open questions: the things we noticed but could not resolve within the budget. An honest list of what an evaluation does not tell you is part of what it does.
